  1. GET /users/stats کار می‌کند، اما نگاهش کنید: منطق کسب‌وکار در روتر، کل جدول‌ها در پایتون و حلقه‌های تودرتو. آن را به سرویس ببرید و بگذارید پایگاه داده با GROUP BY بشمارد. پاسخ JSON نباید تغییر کند.
@router.get('/stats')
async def stats(admin: AdminUser, db: DbSession) -> dict:
    # REFACTOR ME (capstone): business logic in a router, Python loops over whole tables
    users = (await db.scalars(select(User))).all()
    roles = {}
    for u in users:
        if u.role in roles:
            roles[u.role] = roles[u.role] + 1
        else:
            roles[u.role] = 1
    courses = (await db.scalars(select(Course))).all()
    active = 0
    for c in courses:
        if c.is_active == True:  # noqa: E712
            active += 1
    enrollments = (await db.scalars(select(Enrollment))).all()
    statuses = {}
    for e in enrollments:
        statuses[e.status] = statuses.get(e.status, 0) + 1
    counts = {}
    for e in enrollments:
        if e.status == 'active':
            for c in courses:
                if c.id == e.course_id:
                    counts[c.title] = counts.get(c.title, 0) + 1
    top = sorted(counts.items(), key=lambda x: -x[1])[:3]
    return {
        'users_per_role': roles,
        'active_courses': active,
        'enrollments_per_status': statuses,
        'top_courses': [{'title': t, 'students': n} for t, n in top],
    }

۴. یک راه‌حل

پوشه 02_solution یک راه‌حل کامل است که همه ۶۹ آزمونش سبزند. فقط بعد از بازبینی بازش کنید و با کار خودتان مقایسه کنید.

    async def stats(self) -> Stats:
        """Every number is computed by the DATABASE (GROUP BY), not by Python loops."""
        roles = await self.db.execute(select(User.role, func.count()).group_by(User.role))
        statuses = await self.db.execute(
            select(Enrollment.status, func.count()).group_by(Enrollment.status)
        )
        active_courses = await self.db.scalar(
            select(func.count()).select_from(Course).where(Course.is_active)
        )
        top = await self.db.execute(
            select(Course.title, func.count(Enrollment.id).label('students'))
            .join(Enrollment, Enrollment.course_id == Course.id)
            .where(Enrollment.status == 'active')
            .group_by(Course.id)
            .order_by(func.count(Enrollment.id).desc(), Course.title)
            .limit(3)
        )
        return Stats(
            users_per_role=dict(roles.tuples().all()),
            active_courses=active_courses or 0,
            enrollments_per_status=dict(statuses.tuples().all()),
            top_courses=[{'title': title, 'students': n} for title, n in top.tuples()],
        )

    async def update_me(self, user: User, data: UserUpdateMe) -> User:
        user.full_name = data.full_name
        await self.db.commit()
        await self.db.refresh(user)
        return user

    async def change_password(self, user: User, data: PasswordChange) -> None:
        valid, _ = verify_password(data.old_password, user.hashed_password)
        if not valid:
            raise AuthenticationError('The old password is not correct')
        if data.old_password == data.new_password:
            raise BusinessRuleError('The new password must be different')
        user.hashed_password = hash_password(data.new_password)
        await self.db.commit()

۵. بازبینی کد

هر گروه پنج تا هفت دقیقه پروژه‌اش را ارائه می‌دهد و بعد به پرسش‌های گروه دیگر پاسخ می‌دهد. با کد خودتان روی صفحه پاسخ دهید و به فایل و خط اشاره کنید.

  1. مسیر یک درخواست، POST /courses/{id}/enrollments، را از روتر تا پایگاه داده و برگشت دنبال کنید. به کدام فایل‌ها دست می‌زند و چرا هر کدام جداست؟
  2. چرا برای یک دوره هم طرح‌واره Pydantic داریم و هم مدل SQLAlchemy؟ فیلدی نشان دهید که فقط در یکی از آنها هست.
  3. نگاشت‌های تایپ‌دار (Mapped[int]) در برابر سبک قدیمی Column(...) چه چیزی به ما می‌دهند؟
  4. پرس‌وجویی نشان دهید که از N+1 دوری می‌کند. چطور ثابتش می‌کنید؟
  5. چرا طرح پایگاه داده با Alembic تغییر می‌کند و نه با create_all؟
  6. سه جا را نشان دهید که تزریق وابستگی به کار رفته است. آزمون‌ها کدام را جایگزین کردند؟
  7. async کجا واقعاً به این API کمک می‌کند و کجا نه؟ اگر کسی در یک سرویس time.sleep() صدا بزند چه می‌شود؟
  8. جریان ورود را از فرم تا JWT توضیح دهید. چه چیزی در توکن هست و چه چیزی نیست؟
  9. API فرق ۴۰۱ و ۴۰۳ را از کجا می‌فهمد؟
  10. کدام قاعده جلوی مدرسی را می‌گیرد که می‌خواهد دوره مدرس دیگری را تغییر دهد؟
  11. فایل‌های بارگذاری‌شده چطور بررسی می‌شوند و کجا ذخیره می‌شوند؟
  12. آزمون‌هایتان چطور از API محافظت می‌کنند؟ یک آزمون شکست را نشان دهید که به آن افتخار می‌کنید.
  13. کلاینت پایتونی چطور با API صحبت می‌کند و وقتی سرور خاموش است چه می‌کند؟
  14. اگر یک روز دیگر وقت داشتید، اول چه چیزی را بهتر می‌کردید؟

۶. از اینجا به بعد

این دوره عمداً از چیزهایی مثل Redis، صف‌های کار، Kubernetes و استقرار ابری دوری کرد تا روی پایه‌ها تمرکز کند. قدم‌های منطقی بعدی:

  • استقرار: اجرای برنامه پشت یک سرور وب با چند worker و PostgreSQL واقعی.
  • توکن تازه‌سازی (refresh token) برای ورودهای طولانی بدون توکن دسترسی بلندعمر.
  • کارهای پس‌زمینه: فرستادن ایمیل تأیید بدون معطل کردن درخواست.
  • مشاهده‌پذیری: لاگ ساختاریافته با X-Request-ID و اندازه‌گیری زمان پاسخ‌ها.
  • CI: اجرای خودکار pytest و ruff روی هر commit.

۷. خلاصه دوره

فصلیک جمله
۱FastAPI همان پایتون پیشرفته است که با تمام قدرت به کار رفته.
۲مسیر، تابع، کد وضعیت؛ و روترها برای نظم.
۳به کلاینت اعتماد نکن: هر ورودی و خروجی یک طرح‌واره دارد.
۴وابستگی‌ها ساختار را ممکن می‌کنند؛ سرویس‌ها از HTTP خبر ندارند.
۵نوع پایتونی خودِ ستون پایگاه داده است.
۶پرس‌وجو را بخوان، تراکنش را بشناس، قید را تور ایمنی بدان.
۷رابطه راحت است؛ N+1 را ببین و درستش کن.
۸طرح پایگاه داده تاریخچه دارد؛ فهرست‌ها صفحه دارند.
۹رمز را هرگز ذخیره نکن؛ دو شکست ورود را یکسان پاسخ بده.
۱۰۴۰۱ یعنی «کیستی»، ۴۰۳ یعنی «اجازه نداری».
۱۱به نوع فایل اعلام‌شده اعتماد نکن؛ بایت‌ها را بخوان.
۱۲async فقط وقتی کمک می‌کند که هیچ چیز مسدود نکند.
۱۳آزمون شکست به اندازه آزمون موفقیت مهم است.
۱۴یک کلاینت خوب پیچیدگی HTTP را پشت متدهای تایپ‌دار پنهان می‌کند.
۱۵فقط درخواست‌های idempotent را دوباره امتحان کن.
۱۶کدی که می‌توانی از آن دفاع کنی، کدی است که می‌فهمی.
